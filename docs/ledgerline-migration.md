# Ledgerline migration integration

The Ledgerline property maps to `HighVolt-Analytics/Ledgerline`, branch `main`, workflow `deploy.yml`, and the production target. The mapping is visible in the portal, but dispatch remains disabled during migration preparation. The API returns HTTP 423 before contacting GitHub while the property is paused, and it has a second server-side gate that requires `LEDGERLINE_PRODUCTION_CUTOVER_ENABLED=true`. A future dispatch request must provide a 40-character release commit and the exact `DEPLOY` confirmation; the Ledgerline workflow independently checks both against the dispatched `main` commit.

The portal now uses Auth.js GitHub OAuth sessions, server-side GitHub-login allowlisting, operator checks on the dashboard and status/dispatch APIs, same-origin checks on dispatch POSTs, and an eight-hour encrypted JWT session cookie. Auth.js supplies CSRF protection for its OAuth sign-in/sign-out handlers. The dispatch API accepts only a known project id and does not accept repository, branch, workflow, or environment routing from the browser. Unknown payload fields are rejected.

The portal's GitHub API access now uses a GitHub App installation token instead of `GITHUB_TOKEN`. Keep the app private key server-side. Install the app only on the four mapped deployment repositories with repository Actions read/write permission and Metadata read-only. Do not place its credentials in client-exposed variables. Before any live portal release, configure all of these Vercel Production variables without exposing their values: `AUTH_SECRET`, `AUTH_GITHUB_ID`, `AUTH_GITHUB_SECRET`, `AUTH_TRUST_HOST=true`, `DEPLOYMENT_OPERATOR_GITHUB_LOGINS` (exact comma-separated GitHub logins), `GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID`, and `GITHUB_APP_PRIVATE_KEY`. Register the GitHub OAuth callback as `https://webdeployment.highvolt.tech/api/auth/callback/github`.

Do not enable either Ledgerline gate until the owner has approved cutover, the new Hostinger document root and credentials have been verified, production environment approvals are configured, and the live Auth.js callback and allowlisted operator sign-in have been verified. The current live deployment's Vercel protection behavior does not substitute for the source-level session and role checks added here. Vercel deployment protection and project configuration must be verified separately.

The portal repository has no deployment workflow or checked-in hosting configuration. The project is connected to `Ramhighvolt/highvolt-deploy-portal`, not `HighVolt-Analytics/highvolt-deploy-portal`. GitHub reports both repositories as non-forks; their main branches share ancestor `8580f9a06a6b17c208ca04cc44b605945962aba5` but diverged, with three unique commits on the HighVolt-Analytics side and nine on the Ramhighvolt side. Their current trees differ, and no automatic mirroring was found. Treat them as independent codebases with shared ancestry. The live repository must be deliberately changed to deploy the PR code; merging PR #2 alone will not update this Vercel project. Its environment-variable inventory contains legacy `GITHUB_TOKEN` and `GITHUB_OWNER` names; values were not opened. `deployment_status` and `repository_dispatch` event subscriptions are enabled for that connected repository. The current live homepage presents Microsoft sign-in, but API-side access control was not tested. Do not deploy PR #2 or change the live repository integration until the production cutover/update is separately approved and the target repository, auth credentials, and rollback are ready.

Rollback remains an explicit GitHub Actions workflow in the Ledgerline repository; this portal change does not add a portal rollback endpoint. The Ledgerline rollback requires the `Production` environment and a named verified backup.
